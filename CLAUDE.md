# FrameScout — Claude Code project onboarding

## Purpose and product direction
FrameScout is a **local, general-purpose AI image search** tool for large folders of photographs. Users describe a motif in natural language and/or supply example images; the app ranks likely matching local files. Use cases include people, cosplay, objects, vehicles, animals, landscapes and scenes. **Do not re-specialize the UI or algorithms for cosplay, PicDrop, a particular photographer, computer, or image source.** The user wants a convenient and eventually portable Windows application with a simple UI and a clean uninstall.

## Language
- **Project language is English** for everything in the repository and on GitHub: code, identifiers, code comments, UI, generated outputs, docs, commit messages, PR titles/descriptions, review comments and skills. CLIP prompts are English anyway.
- UI strings, the HTML gallery, engine log/error messages and the `.bat` messages are English since I7. Remaining German names, kept for compatibility: the legacy crop label `Gesamtbild` in old cache rows (shown as "Full image" via `framescout_core.crop_label`) and the thumbnail folder `results/vorschaubilder/` of older runs (no longer written; new runs use `results/thumbnails/`).
- Chat with the user may be in German.

## Status
Current baseline: **v1.1, prototype**, with a Streamlit frontend and a separate Python CLI engine. The git repository (`main` on `enqii/frame-scout`) is the source of truth; inspect the code before making changes.

One full end-to-end search run on Windows has been confirmed (I6): `run.log` from the original checkout shows 4,997 photos, 6 search profiles, CLIP on CPU, YOLO person detection enabled, 0 errors (2,609 new analyses + 2,388 from cache, i.e. a resumed run) and 6 HTML galleries written. The project `.venv` used for that run is Python 3.14.8 with torch 2.14.1+cpu (per `.venv/pyvenv.cfg` and the installed torch package; `run.log` itself does not record versions). The log also shows the QuickGELU warning (E1, fixed since: that run's embeddings came from the GELU variant). This is a single CPU-only run, not a test suite: CUDA beyond one engine smoke run (the installer option and GPU use exist since PR #8; one run with `--device cuda` on an RTX 4070 with torch 2.14.1+cu130 and 300 synthetic photos, embeddings matching the CPU run; the CUDA install itself, the app on a GPU, real photos and other GPUs are untested, I11), other Python versions, a fresh install on another machine and the edge cases in the backlog are **not** verified. Treat syntax checks, unit tests and a real model run as distinct kinds of evidence, and do not call the app production-ready.

## How to run (Windows)
1. Clone the repository (or download and extract the ZIP) into a directory you control. Install a compatible Python if needed.
2. Double-click `Install-FrameScout.bat` (prefer keeping all packages inside `.venv`). It offers GPU support if it finds an NVIDIA driver; `Install-FrameScout.bat cpu|cuda` chooses the PyTorch build directly. Never run the `cuda` variant on a development PC without approval: it downloads about 2.5 GB.
3. Double-click `Start-FrameScout.bat`; local browser URL `http://127.0.0.1:8501`.
4. In the app, choose an existing local folder (including subfolders), configure search profiles, review AI settings, start the search and open HTML results from `results/`.
5. ZIP/downloaded online albums need to be separately downloaded/extracted by the user; FrameScout itself has no online-service integration.

Manual commands for development (after installation):
```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1 --server.port 8501
.\.venv\Scripts\python.exe framescout_engine.py .\photos --profiles .\profiles.json --output .\results --device cpu --batch-size 8 --top 150
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt   # once
.\.venv\Scripts\python.exe -m pytest
```
On a fresh clone, `profiles.json` exists only after the first app start; use `--profiles .\profiles.example.json` until then. Do not claim these commands work on a given Python build without running them in that environment. For smoke runs during development, write output under `.tmp/` (e.g. `--output .\.tmp\smoke-results`), never into the user's `results/`.

## Current search pipeline
- Uses OpenCLIP `ViT-B-32-quickgelu`, `pretrained='openai'` (`framescout_core.CLIP_MODEL`; the OpenAI weights need QuickGELU, plain `ViT-B-32` would run them with GELU, E1), for normalized text and image embeddings. No LLM is required. Four generic English prompt templates are derived from each profile's name and optional context, plus two extra templates if `features` is provided (`load_profiles` reports their number as `generated`); user-defined `prompts` are appended.
- Search terms are **English only** (E3, user decision in PR #12): the model understands practically only English and nothing is translated. The profile tab shows a hint and labels the motif, context, features and custom search text fields "in English"; README section "Search terms in English". Hint text only: do not add a language check, warning or translation without a new user decision. A multilingual model is E21 (`xlm-roberta-base-ViT-B-32`: about 1.47 GB, `transformers`, re-analysis of every photo; a hold point).
- Optional Ultralytics `yolo11n.pt` person detection (`classes=[0]`) extracts individual person crops **in addition to the full original image**. Detection is deliberately optional for non-person motifs; the detector runs on the CLIP device (E14), one photo per call under a lock (several photos per call: E18).
- Analysis pipeline (E2): uncached photos are stat-ed, decoded, searched for persons and preprocessed in threads – up to four without person detection (`DECODE_THREADS`), two with it (`DETECTION_DECODE_THREADS`, so at most two full-resolution photos are in memory while the detector runs one photo at a time) – at most `max(2 × threads, --batch-size + threads)` photos ahead (`framescout_core.prefetch`); the shared YOLO detector is called under a lock. The crops of several photos are embedded in one CLIP forward pass of at most `--batch-size` crops (`framescout_core.group_batches`; a photo with more crops is a group of its own), and each group is committed to SQLite in one transaction; if that fails, its photos are stored one by one, so only a failing photo is counted as an error (`framescout_core.store_group`). Without person detection JPEGs are decoded at 1/2, 1/4 or 1/8 scale (`Image.draft`) down to twice the CLIP input size (`framescout_core.draft_size`, 448 px); with person detection they keep full resolution. Gallery thumbnails are drafted the same way (to 760 px for 380 px thumbnails). Cache signature: with detection it is unchanged (the features are identical); without detection it names the drafted decoding (`DRAFT_DECODING`, user decision in the PR #7 review), so the first detection-off run after E2 analyzes every photo once more and drafted and full-resolution embeddings never mix (they agree to a cosine similarity ≥ 0.999 on a 202-photo sample).
- Scoring (`framescout_scoring`, E4/E5): the generated templates of a profile are averaged into one normalized query (prompt ensemble); each custom prompt stays a query of its own, and a crop's text score is its best cosine similarity with one of these queries (user decision in PR #11: custom prompts keep their "any of these" meaning). If reference images exist, visual score = max over reference vectors. Per profile and run, the text and visual scores are z-scored separately over all crops of the searched photos (mean and standard deviation of this search), then combined as `(1-reference_weight)*z_text + reference_weight*z_visual` (a channel with weight 0 needs no spread) (default reference weight 0.3, `framescout_core.DEFAULT_REFERENCE_WEIGHT`, also the engine's `--reference-weight` default; 0.35 before E5, changed after the local evaluation in PR #11, E20); with fewer than `MIN_SCORES` (10) crops or a spread below `MIN_SPREAD` in either channel, both channels use the raw cosine scores as before E4/E5. The best full-image/crop score represents a source photo. The gallery shows the normalized "Score" ("Similarity" for raw scores) with the raw text and image similarity of that crop in small text. A cache row that is broken (labels and vectors do not match, scores not finite) is logged as `CACHE ERROR` and skipped (`framescout_scoring.photo_scores`), and `spread` ignores non-finite values. Scores depend on the folder searched; they are relative search heuristics, not probabilities or guaranteed identification. Scoring needs no cache change: it runs on the cached features at query time.
- Feature rows are stored in `results/cache.sqlite3` per resolved file path + engine/config signature (`framescout_core.feature_signature`: `ENGINE`, whether person detection is on and, only if it is, the detector settings; pinned by golden values in `tests/test_signature.py`), checked against modification nanoseconds and size. Image embeddings are serialized in float16; profile queries can reuse existing image features. Changes to detector settings invalidate the cached feature signature; bump `ENGINE` whenever cached embeddings become incompatible (model, weights, preprocessing, crops). Rows of other signatures are never deleted (E7, E11).
- Outputs one ranked `.html` file per profile (`<slug>.html` from `framescout_core.profile_slugs`: ASCII transliteration, `-2`, `-3`, … on collisions in profile order, hash fallback), with separate JPEG thumbnails in `results/thumbnails/` and `file://` links to originals. Keep the output folder intact; exporting an HTML file on its own does **not** embed thumbnails. Local paths may not work on another computer.
- After the galleries the engine writes `results/results.json` (`framescout_core.write_results`, format 1): run start and end, photo folder, settings, number of photos and per profile its name, `search_fingerprint` (hash of its search texts and reference paths, relative to the profiles file's folder when inside it, so a moved project folder changes nothing), gallery file name, `normalized` and the cards (rank, path, relative path, crop label, score, raw text/visual similarity, the two caption lines, thumbnail name) in gallery order. Written only when the export completes, so a stopped search leaves the previous file (galleries already rewritten: E24). The app reads it (cached by mtime and size) instead of deriving file names from the current profile list (A12). The gallery's "Open" uses `os.startfile` and only for an existing file with an `EXT` suffix (`openable_photo`), "Folder" `SHOpenFolderAndSelectItems` via ctypes on Windows (`explorer /select,` did not select a file with a comma in its name), `open`/`xdg-open` elsewhere (untested, A19); they act on the computer the app runs on.
- Supported inputs: JPG, JPEG, PNG, WebP, BMP, TIF, TIFF, recursively. The engine excludes the output folder if nested in the input root.

## Profiles schema
```json
{
  "profiles": [
    {
      "name": "Red car",
      "franchise": "Vehicles",
      "features": "red bodywork, four wheels",
      "reference_images": [],
      "prompts": []
    }
  ]
}
```
`franchise` is a legacy internal field name; in the UI it means optional **Context / origin** (in English, E3), not necessarily a media franchise. Reference paths are interpreted relative to the profile JSON file directory. `app.py` uploads references into `references/<slug>/`, or `<slug>-2`, `-3`, … if that folder holds references of another profile (`framescout_core.reference_folder`, A1). The folder follows the profile name (user decision): on a rename, `app.py` gives the profile's own files under `references/` a hard link (or copy) in the new folder, saves `profiles.json` with the new paths, rewrites the moved paths in `profiles.json.bak` (`update_backup_references`, so restoring the backup keeps working) and only then removes the old names and an emptied old folder; a failed save removes only the new names, a failed backup rewrite keeps the old names. Files of other profiles, leftovers, missing files and paths outside `references/` are never moved; otherwise existing reference paths are left as they are. Uploads are named `reference-<n>` with the next free number and never overwrite an existing file. Never silently delete or overwrite user profiles/references. There is also a legacy CLI option `--character`; consider backward compatibility before renaming it.

## Current UI / runtime details
- Settings are kept in `settings.json` in the project folder (gitignored, A8): the app reads it on every rerun (so a reload, a restart, another tab or session, also during a running search, shows them; a read failing while another session replaces the file is retried) and saves the values changed in a page run, merged into the current file (`framescout_core.save_settings`). The settings widgets have keys (`setting_<name>`) and get the saved values through `st.session_state`; never pass them `value=`/`index=`, which gives a widget a new identity after every save and drops the next change (PR #10 review). `framescout_core.reconcile_settings` does the sync on every page run with two session records: `settings_seen` (the saved value last taken from or written to the file, as written, e.g. rounded) and `settings_shown` (the value the widget showed; they differ for slider noise and for the device substitute). A widget that differs from `settings_shown` was changed in this session and is saved; a saved value that differs from `settings_seen` came from another session and is shown, so the latest action wins. A Start in a page run that took over such values is refused once with a note. `save_settings` holds a `RunLock` on `settings.json.lock` around its read-merge-write (sessions are threads of one process). The widgets take their ranges from `SETTING_RANGES`; `system_info` (which imports torch) runs in the AI settings tab, so the profile tab is drawn first. A read that still fails with an `OSError` (file in use) gets a different message than a corrupt file (`ValueError`). Only values that differ from the defaults are written, so the default photo folder follows a moved project folder; unknown keys are kept. Keys follow the CLI options; defaults (`default_settings`): `photo_folder` `BASE/photos`, `device` `auto|cpu|cuda` ("cuda" is offered only if `torch.cuda.is_available()`, A7; a saved device PyTorch cannot use is shown and used as "auto" but stays saved until another one or "Use auto from now on" is chosen), `batch_size` 8, `top` 150, `person_detection` on, `max_persons` 12, `person_confidence` .30, `reference_weight` 0.3 (`DEFAULT_REFERENCE_WEIGHT`; 0.35 before PR #11, a saved value is not migrated). `read_settings` checks each value against the range of its widget (an invalid one falls back to its default with a warning, `save_settings` removes it with the next save; floats are rounded, as sliders return values like 0.30000000000000004); an unreadable file is never replaced (like `profiles.json`, A2) and the page keeps the settings it shows.
- Run state (A4/A5): the engine holds an operating-system lock on `<output>/run.lock` (`framescout_core.RunLock`: Windows byte-range lock, `flock` elsewhere; the OS releases it when the process ends in any way, also after `kill()`) and writes `<output>/run-status.json` (`StatusReporter`: format, pid, phase `scanning`/`loading`/`analyzing`/`scoring`/`exporting` → `finished`/`failed`/`interrupted`, done/total of the phase, new/cached/errors, exit code, message; atomic, at most one write a second, best effort). It takes the lock after the cheap argument checks (after `import torch`), waiting up to five seconds; if another search holds it, it exits with code 3 (`EXIT_BUSY`). A missing photo folder is an error before the lock only if the output folder does not exist yet (no folder is created for a mistyped call); otherwise it is reported in the status file. The final phase comes from the exit code (`final_status`: 0 finished, 130 interrupted, others failed).
- The frontend spawns the engine via `subprocess.Popen` and redirects stdout/stderr to `run.log`. `start_run` takes the run lock (1 s timeout: every open tab probes it every two seconds), truncates `run.log`, spawns the engine and writes the status `starting` with the child's pid, then releases the lock to the engine; if that status cannot be written it ends the child again. A start while the lock is held, or while a `starting` status names a live engine process, is refused. "Running" is derived on every rerun and every two seconds (fragment) from the lock and the status file (`run_active`, read once per page run; `engine_alive` checks via `psutil` that the pid's command line contains `framescout_engine.py` and that the process existed when the status was written, `started_in_time`, so a reused pid does not count), not from the session's process handle, so a reload, another tab or session shows the run and can stop it; the fragment reruns the page when the state changes. On Windows the venv's `python.exe` is a launcher: `Popen.pid` is the launcher, the pid in the status file the engine (its child); killing the launcher also ends the engine (verified).
- Stop (`stop_run`) reads the status again, terminates the session's process and the status file's engine with their child processes (`psutil`), kills what is left after five seconds and then waits up to ten seconds for the lock (Windows may release it a moment after the process ended) and marks the status `interrupted` / "Stopped in the app." if its pid is one of the ended processes (otherwise another start has replaced it); if it cannot, the app says so. Each embedded group of photos (at most `--batch-size` crops, unless one photo has more) is committed to SQLite, so a stop loses at most the group in progress. A `KeyboardInterrupt` in the CLI cancels the queued decoding and exits with code 130. Not a background job manager: the engine is a child of the Streamlit process, and closing the `Start-FrameScout.bat` window is not tested with a running search.
- Hardware info is detected dynamically via `platform`, `os`, `psutil` and `torch.cuda`; `auto` chooses CUDA if PyTorch detects it, otherwise CPU. Do not hardcode the CPU/GPU model or the user's RAM. A GPU may exist without CUDA support; the app tells a CPU build of PyTorch (`torch.version.cuda is None`) from a CUDA build that finds no usable GPU (e.g. a driver too old for it); the hint says to close FrameScout, run `Install-FrameScout.bat cuda` and start it again, since the running app keeps the loaded torch and the cached `system_info`.
- The Windows batch scripts set cache/temp environment variables under the project directory (`TORCH_HOME`, `HF_HOME`, `YOLO_CONFIG_DIR`, `XDG_CACHE_HOME`, `TMP`, `TEMP`), aiming for easy cleanup. Some dependencies may still leave user-level caches (e.g. Ultralytics writes `%APPDATA%\Ultralytics\settings.json` when imported without `YOLO_CONFIG_DIR`, I10); do not promise perfect portability or no residual files.

## Engineering principles / known areas to test
1. Preserve general-purpose wording and behavior across UI, presets, prompts, docs, filenames and outputs.
2. Keep all user image data local; do not add cloud uploads, tracking, or network services without explicit consent. First use downloads model weights and pip packages.
3. Separate frontend and engine; maintain a working CLI and a usable CPU-only path (32 GB RAM and a dedicated GPU must **not** be prerequisites).
4. Save user state safely, validate paths and profiles, protect data during migrations; avoid overwriting `profiles.json` and user-selected photos/results.
5. Add focused tests without requiring full model downloads. Profile loading, reading/saving the app's `profiles.json` and `settings.json`, reference folders, prompt generation, slug handling, progress lines (A11), the run lock and status file (A4/A5), thumbnails of the export (E6), the cache signature, the pipeline helpers for batching/prefetching (E2), the scoring (E4/E5) and the result file with the gallery helpers (A12) are covered by `tests/` (via `framescout_core` and `framescout_scoring`); still missing: cache reuse and the engine's decoding itself (`open_image` with `Image.draft` needs Pillow, which CI does not install). Add a small integration smoke test for real models when feasible.
6. Potential current quirks to investigate rather than assume solved (most are tracked in `BACKLOG.md`): the cleanup of E7 must keep thumbnails and galleries that `results.json` references (E23); the app saves its whole profile list, so edits by another session in between are overwritten (A13); an empty photo folder field counts as the app's working directory (A16); result file downloads do not contain thumbnails (ZIP export: P4 (C), A18); `app.py` itself has no automated tests (A4/A5 were checked once with Streamlit's `AppTest` and real engine runs, and manually in a browser: start, reload, second tab, Stop – successful, user report 2026-10-21; closing the `Start-FrameScout.bat` window during a run is still not tested; A8's settings widgets were checked with `AppTest` and in headless Edge driven over the DevTools protocol – `AppTest` alone is not enough evidence for widget behavior, as it does not run the browser frontend; the result gallery of P4 (A) was checked with `AppTest` and in headless Edge, and its "Open"/"Folder" buttons once on Windows 11 with synthetic photos under `.tmp/`); Python 3.14 has been verified for one CPU run only; absolute paths/HTML link portability. The UI's dynamic system information is informational, not a hardware benchmark.
7. Never conflate a similarity score with certainty. Explain that large group photos, subtle subjects and artwork-to-photo reference comparisons can yield false positives/negatives.

- Roadmap work (`BACKLOG.md` → "Roadmap") goes through the PR workflow below; start it with `/roadmap`. The skill is user-invoked only (so subagents can never start a second orchestrator): if the user asks in words to continue, resume or check the roadmap, ask them to type `/roadmap` instead of improvising the workflow.
- For ad-hoc requests: first read `README.md`, `BACKLOG.md`, `app.py`, `framescout_engine.py`, `profiles.example.json`, `requirements.txt` and both `.bat` files. Summarize the current code state and risks before changing architecture. If the request is unspecified, ask which improvement to implement next.
- For each change, report modified files, migration/backward-compatibility consequences, test commands and which tests were actually executed (vs. not executed).
- Keep `README.md`, `BACKLOG.md` (check off items, add new findings with IDs) and this `CLAUDE.md` current when behavior changes.
- Avoid claiming the app is production-ready without an actual end-to-end test.

## PR workflow
The roadmap is implemented semi-autonomously, **one pull request per roadmap item**. The `/roadmap` skill (`.claude/skills/roadmap/SKILL.md`) is the orchestrator: it is stateless, reconstructs the current state from git and GitHub on every start and spawns subagents (implementer, reviewer) with the briefs in the same folder. **This section is the single source of the workflow rules**; the skill and the briefs contain procedures and commands and refer back here instead of repeating the rules.

- **Strictly sequential:** the next roadmap item is started only after the previous PR has been merged.
- **Branch naming:** `<type>/<id>-<short>`, e.g. `fix/a1-unique-reference-names`, `chore/p0-workflow-english`. Branch from an up-to-date `origin/main` without tracking it (`git switch --no-track -c <branch> origin/main`) and always push with the branch named (`git push [-u] origin <branch>`); never push to `main` directly, never force-push, never discard work you did not create.
- **Commits:** atomic Conventional Commits (see below), each pushed immediately after it is created, so that no work exists only locally.
- **Draft PR early:** right after the first commit, open a draft PR (template: `.github/pull_request_template.md`) and label it `fs:in-progress`.
- **State labels** (exactly one per roadmap PR):
  | Label | Meaning |
  |---|---|
  | `fs:in-progress` | implementer is working on the branch |
  | `fs:needs-review` | implementation done, PR marked ready, waiting for the reviewer |
  | `fs:review-done` | reviewer posted `/code-review` findings as PR comments |
  | `fs:ready` | findings addressed or declined with reasons; waiting for the user's merge approval |
- **Review:** a fresh reviewer agent runs `/code-review medium <PR> --comment` and must not change code. The implementer then verifies every finding technically, fixes it or declines it with a reasoned reply on the comment thread, and summarizes "addressed / declined" in the PR.
- **Out-of-scope findings go into the backlog:** anything found while working on a PR that is outside its scope – valid review findings that are deferred, discovered limitations, new bugs – is added to `BACKLOG.md` **in the same PR** as a new item with the next free ID of its group (E/A/I). A declined review reply that defers work names that backlog ID. `BACKLOG.md` is the single source of truth for open work; do not create GitHub issues.
- **Merge:** only after the user's explicit approval in chat and with all CI checks of the approved head commit green, as a rebase merge (`gh pr merge <PR> --rebase --delete-branch`), followed by worktree and branch cleanup and updating local `main` – the exact procedure is in `/roadmap` → "Merge".
- **Definition of done:** all checklist items of the PR template are true – summary and backlog IDs, modified files, migration/compatibility consequences, tests executed (with output) vs. not executed, CI checks green, `BACKLOG.md`/`README.md`/`CLAUDE.md` updated where needed, user data untouched, review findings addressed or declined.
- **Hold points** – the implementer stops and returns a question instead of guessing; the orchestrator asks the user (and posts the question as a PR comment once a PR exists):
  - product/design decisions (e.g. P4b stronger or multilingual search models, P4 gallery/UX, P5 distribution);
  - breaking changes: `profiles.json` schema, CLI options, cache invalidation, folder renames;
  - new dependencies or downloads, unless the roadmap item explicitly names them (e.g. `pytest` in step (1));
  - anything that cannot be verified locally (e.g. CUDA without an NVIDIA GPU) → the PR is marked "not runtime-tested";
  - changes to search quality → first a small local evaluation set (kept outside the repo).
- **User data protection:** never modify, delete or commit the user's working files: the local `profiles.json`, `settings.json`, `photos/`, `references/`, `results/`, `run.log`. `profiles.json` is gitignored since I7; never add it back to the repository (the shipped examples live in `profiles.example.json`). Stage files by name, never in bulk. Tests use pytest's `tmp_path`; smoke runs read and write only under `.tmp/` (no `..` in `--output`) and set `TORCH_HOME`, `HF_HOME`, `XDG_CACHE_HOME` and `YOLO_CONFIG_DIR` to the main checkout's `.cache/` first, as the `.bat` files do; a download that would still be needed is a hold point.
- **Pausing and resuming:**
  - Same PC: `claude --continue` or `claude --resume` restores the orchestrator session. Background subagents do **not** survive exiting Claude Code, but their pushed commits and PR comments do; `/roadmap` picks up from the PR labels.
  - Other PC: clone the repo, run `Install-FrameScout.bat`, start Claude Code in the folder and run `/roadmap`; it reconstructs the state from GitHub.
  - Not transferable: unpushed local work (worktrees under `.claude/worktrees/`) and subagent context.
- **Permissions:** `.claude/settings.json` pre-approves the routine git/gh/pytest commands of this workflow. Pushes are pre-approved only as `git push [-u] origin <type>/…`; a bare `git push`, `gh pr merge`, force/reset variants of `git branch`/`git switch`, bulk staging (`git add -A`/`.`, `git commit -a`, anything naming `profiles.json` or `settings.json`) and engine smoke runs ask; force pushes, `--mirror`/`--all`/`--delete`, pushes naming `main` and `git reset --hard` are denied. Rules are evaluated deny → ask → allow and match the command text with `*` wildcards; they steer the agent but are **not** a security boundary (`git -C . push`, `sh -c …` or an absolute path to `git` are not matched, and `main` cannot be branch-protected on the current GitHub plan, see I8). Personal overrides go into `.claude/settings.local.json` (gitignored).

## Git and commits
- Repository: private GitHub repo `enqii/frame-scout`, default branch `main`.
- Git identity: repo-local `enqii <24801755+enqii@users.noreply.github.com>` (`git config user.name` / `user.email` in the repository). Never commit with the global (work) identity; check `git config user.email` in new clones and worktrees.
- GitHub CLI: `C:\Program Files\GitHub CLI\gh.exe` (may not be on `PATH`; in Git Bash use `"/c/Program Files/GitHub CLI/gh.exe"`).
- Commit messages **must** follow the [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) specification: `<type>[optional scope][!]: <description>`, optional body, optional footers.
- Types: `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Breaking changes (e.g. incompatible `profiles.json` schema or CLI options) are marked with `!` and a `BREAKING CHANGE:` footer.
- Suggested scopes: `engine`, `app`, `install`, `profiles`, `deps`, `backlog`, `ci`.
- Description and body in English, imperative mood, lowercase start, no trailing period; reference backlog IDs where applicable, e.g. `fix(app): stop overwriting reference images (A1)`.
